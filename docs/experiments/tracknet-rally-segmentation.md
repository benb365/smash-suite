## 为什么这次有区别

| 项目 | 旧尝试 | 本次候选 |
| --- | --- | --- |
| 判断依据 | 球员框底部的运动，打球与走动难区分 | 直接观察羽毛球飞行 |
| 输入频率 | 实际约 2.5 次/秒 | 25fps，每三张连续帧输出三张热图 |
| 自动球场识别 | 外部集成在球场预处理失败，未产出可用回合 | 不调用；人工场地范围仅作宽松图像过滤 |
| 保留策略 | 10 秒提前量和事后合并掩盖边界 | 持续飞行确认、静止球不续期、容忍缺球间隙 |
| 间歇干扰 | 走动或捡球容易激活 | 短抛球轨迹和孤立位置跳变不成为回合 |

旧输出的 7 个大区间存在 5 次跨回合合并；本次 11 个区间没有跨回合合并。旧算法较快，但人物运动不能可靠区分对打与间歇，调整补时解决不了这个问题。见[旧实验对照](../../backup/docs/experiments/legacy-rally-segmentation.md)。

## 实际算法

1. 原画面 RGB、归一化，按原模型方式缩放至 512×288；三帧拼成 9 通道。复用 SoloShuttlePose 的 TrackNet 架构和本地权重，没有训练或下载新模型。
2. 热图置信度至少 0.6，取最大连通区域中心。图像范围由已有人工场地外框向左右扩展画宽的 5%、向上扩展画高的 40%、向下扩展 2%。这不是地面投影，允许球飞到远端底线上方。
3. 在最近 80–200ms 内计算位移速度，使用 1920px 画宽基准的 100–4000px/s 范围；要求三个连续运动观察，过滤静止球、小抖动和单次位置跳变。
4. 候选飞行跨度至少 2.2 秒才确认回合。确认后允许稀疏轨迹继续回合；超过 1.6 秒没有有效运动，输出第一次飞行到最后一次运动的区间。
5. 无事后跨回合合并，无 EOF 强行结束。新轨迹到来前先检查旧回合是否已结束，避免连接到下一次抛球。

**2.2 秒条件有明确代价：发球直接失误、一拍得分等极短回合可能被过滤。这是当前候选的局限，下一步优先解决。**

三帧处理最多需要 80ms 输入缓冲；前两帧的热图只在第三帧到达后使用。输出 `emitted_at_ms` 是当下输入帧时间。源时间轴结束确认延迟为 1.64–1.72 秒，尚未测摄像头采集、实时编码和界面显示的总延迟。

## 重现

从仓库根目录，在可访问本机 GPU 的普通终端执行：

```bash
models/SoloShuttlePose/.venv/bin/python backend/tests/rally_benchmark/run_tracknet.py --device mps --output models/SoloShuttlePose/.runtime/tracknet-rally-live
```

只重放保存的轨迹，不再运行模型：

```bash
models/SoloShuttlePose/.venv/bin/python backend/tests/rally_benchmark/run_tracknet.py --reuse-trace --preview
```

第一个命令逐帧执行模型和分割器；第二个使用同一分割器和输入输出校验，保留模型观察的实际可用时刻，不使用未来帧。预览默认编码为 MP4V；本轮交付视频另用 macOS AVFoundation 转为浏览器可播放的 H.264。

仓库模型环境已有 `torchsummary`，直接复用，无新增项目依赖。CPU 可用 `--device cpu`，GPU 为 MPS；本轮沙箱内 MPS 不可见，宿主环境可正常访问。吞吐包括视频读取、模型、分割和日志写入，不包括预览编码，也没有做长期温度/降频测试。

`backend/app/vision/tracknet_rally.py` 为模型适配和分割器；`backend/tests/rally_benchmark/run_tracknet.py` 为实验及预览导出；不扩展旧人物分割器，不改正式 API。输出中的配置和哈希用于复现；实验运行器仍针对现有 seed 标签。
