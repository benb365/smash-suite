# 工作流控制分支判断

依据候选 skill《单任务持续开发与验收》。以下均为模拟控制判断，不代表执行了功能开发或验收。

## 情景 A

**决定：不派发开发。**“帮我持续做这个功能”尚未确认启用流程、范围与验收标准。启动规则要求适用时先询问是否启用，并确认范围、方案和功能验收标准；没有确认前不派发开发，也不自行缩小或替换标准。应把这些待确认项交回主控向用户确认，确认前不开展依赖它们的开发。

## 情景 B

**决定：暂不开发。**用户已确认启用、范围与方案，但功能验收标准仍未答复。启动规则要求同时确认验收标准；不能因为其余决策已确定就自行拟定或代替用户确认。主控应先取得该标准，再派发开发。

## 情景 C

**第二轮报告到达后：调整排查方向。**已收到两个独立验收失败报告，且两轮没有新证据、目标改善、通过、阻塞解除或推进后续的新证据。skill 明确说连续两轮没有这些进展时调整排查方向；重复检查或改写结论不算进展。应由主控决定返工方向或询问用户，不能用相同检查重跑冒充进展。

**第三轮仍同样失败：停止相关运行，保存材料并等待用户。**skill 明确规定连续三轮没有实质进展时停止相关运行并等待用户。主控不应继续启动同样的验收循环。

## 情景 D

**决定：不能按当前指标宣布改善，也不能自行设定替代数值指标。**当前边界绝对误差把提前剪掉有效对抗与落地后多留等量计分，和用户目标“不要剪掉有效对抗”存在具体冲突；现有样本还显示最后一次击球丢失。启动规则要求从使用目的和错误代价判断指标是否有效；发现不符时说明具体案例和风险、建议并请用户确认，不得自行设定或改变验收口径。主控应向用户说明冲突并请求确认新的口径后再判断改善。

## 情景 E

**决定：恢复原任务的既有材料和执行上下文，并重算停滞轮数。**用户明确恢复后，skill 要求继续使用原认领、分支 `codex/example`、worktree `/private/tmp/example-task` 和记录；不另起新任务上下文。停滞计数应重新计算，原来的连续停滞计数 2 不直接沿用为恢复后的连续计数。材料仍留在 `docs/ai/example`。

## 情景 F

**三个验收步骤通过、但只有计划确认时：**可以在任务分支本地提交已验收实现并保留 worktree；任务分支记为“已完成，待人工确认”，develop 仍记“进行中”并保留认领。不得合入或推送。skill 明确指出计划确认不代表集成许可。

**用户要求 README 再补一个例子时：**在原任务分支返工，并对修改后的交付复验。不要把先前通过视为修订版也已通过。

**修订后的实际交付获明确合入批准后：**主控才一次集成到 develop，移除已结束认领、更新状态，并验证受影响范围。此时可按用户批准完成集成；skill 同时明确此阶段之外不推送或合入。其“交付后等待用户决定下一项任务”的边界仍适用。

## 情景 G

**决定：验收不通过。**代码检查通过，但 README 与实际功能及需求相反，违反“一轮”中检查文档准确性的要求；功能、代码或文档任一项失败都要退回主控，说明证据、缺口和建议。因此下一角色是主控，由主控决定返工或询问用户。验收者只在自己的 `output.md` 记录文档矛盾及证据、缺口和建议，不修改实现或标准，也不直接联系开发；主控负责中转结果。

## 情景 H

**skill 明确规定：**“验收固定本轮版本”，但没有明确规定在开发 agent 并行修改时怎样停止其工作、怎样锁定或记录具体检查版本，也没有明确规定最终提交包含未经验收代码时的处置流程。

**据此作出的推论（不是 skill 原文规则）：**若最终提交比验收固定的版本多出未检查代码，则独立验收结果不能证明最终提交已通过。主控应把新增差异视为尚未验收，安排针对该最终版本的独立检查；在得到对应结果前，不应把最终提交标记为验收通过。需要避免版本漂移时，主控可在派发时明确固定提交或快照并协调暂停并行修改，但这属于执行上的控制建议，不是候选 skill 明文规定的机制。

## 情景 I

**完整历史：未明确允许或禁止。**候选 skill 没有规定能否把完整对话历史传给子 agent。它规定主控维护任务材料并中转用户决策与双方结果，给子 agent 的工具指令只包含文件路径和生命周期指令，业务要求写入文档；因此应按这些明确的材料边界组织任务，但不能把“禁止传完整历史”说成 skill 原文。

**子 agent 互发修复建议：明确禁止直接交流。**skill 写明开发和验收不直接交流，也不读取对方通信目录，主控是唯一中转。因此两个子 agent 不能互相发送修复建议；需要传达的建议由主控中转。skill 没有进一步规定其意见内容或格式。
