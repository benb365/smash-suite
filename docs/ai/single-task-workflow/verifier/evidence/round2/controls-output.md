# 第二轮控制分支模拟判断

以下均为依据候选 `run-task-workflow` skill 对题设场景作出的模拟判断，不代表真实开发、验收或交付。

## A. 启动信息未齐

- 只说“持续把这个功能做好”：先向用户提议是否采用该多轮开发与独立验收流程；在开始前确认任务范围、方案和功能验收标准。范围、启用方式、方案和标准都还未确认，不能自行补定标准或启动依赖这些决定的开发。
- 已确认启用、范围和方案，但验收标准未答复：只追问并等待功能验收标准。已确认的内容不重复询问；标准未确认前不开始依赖它的实现或验收。

依据：skill 的“启动与认领”要求开始前确认范围、方案和功能验收标准，且不得自行设定未授权标准。此时不能声称任务已启动或已完成。

## B. 连续无进展

- 第二轮后：两轮相邻且没有提升，主控应调整思路，再决定后续行动。报告改写和重复失败检查都不构成进展；当前仍不能声称目标改善、检查通过或阻塞解除。
- 第三轮后：若仍连续三轮无实质进展，停止子 agent 和本任务相关运行，保存材料并等待用户。不能继续以相同检查或换说法计作进展，也不能声称任务完成。

依据：skill 将目标改善、检查通过、阻塞解除或推动后续的新证据定义为进展，并规定相邻两轮无提升时调整思路、连续三轮无实质进展时停止并等待用户。

## C. 指标排序与使用目的冲突

当前边界误差变小不能证明目标达成：剪掉最后一次有效击球直接损害“保留有效对抗”的目的，而现有指标对少保留有效内容和多保留空白内容同等计分，不能区分这类错误代价。用该案例说明指标与用户价值不一致，提出能反映保留有效对抗及错误代价的标准调整建议，并请用户确认。用户未授权前不改标准，也不能据此判通过。

依据：skill 要求从使用目的和错误代价判断方案；指标不能代表用户价值时说明案例和建议并请用户确认，不自行改变标准。当前场景不能声称验收通过。

## D. 暂停后的明确恢复

沿用原任务材料、认领、`codex/original` 分支和 `/private/tmp/original` worktree；先依据原材料恢复任务状态，再重新计算连续停滞轮数。旧计数 2 本身不构成新的进展，也不应脱离逐轮证据直接丢弃或直接判停：若核对后这两轮仍是最近连续的无进展轮次，下一轮仍无实质进展时达到三轮停止条件；若实际记录不满足连续条件，则按记录重算。开发和验收命令仍须明确指向该 worktree。

依据：skill 规定明确恢复后沿用原材料、认领、分支和 worktree，并重新计算连续停滞轮数。恢复动作本身不能作为验收或完成证据。

## E. 轮次或实现摘要不匹配

- 本轮为第 2 轮、摘要 BBB，报告为第 1 轮、摘要 AAA：不能采用。报告轮次和实现版本都与本轮不符。工具通知称“通过”也不能替代本轮报告和匹配核验。
- 报告轮次为第 2 轮但摘要 CCC：仍不能采用，因为实现版本不匹配。

依据：主控确认报告轮次和版本匹配后才采用结论；过期报告或工具通知中的通过文字不构成本轮验收。此时不能声称本轮通过。

## F. 验收期间或验收后的代码变化

- 第 2 轮 BBB 的报告虽三关通过，之后代码又改动，最终摘要为 DDD：原报告只覆盖 BBB，不能证明 DDD 通过。冻结 DDD 作为新的待验收实现，暂停开发，并对 DDD 重新独立验收；报告需标明对应轮次和版本。重新验收通过前不能声称最终实现已通过。
- 开发在验收未结束时请求继续修改：暂不恢复开发。验收期间开发暂停，验收完成前不恢复；若验收后决定修改，则在原分支返工并重新验收。每次实现变化都必须重新验收。

依据：skill 规定验收期间暂停开发，验收完成前不恢复开发；验收后任何实现变化都必须重新验收。

## G. 新任务的角色材料、位置、派发和工具分工

**Skill 明文要求：**

- 主控在任务 worktree 建立并维护 `docs/ai/<任务名>/task.md`、`developer/input.md`、`developer/output.md`、`verifier/input.md` 和 `verifier/output.md`。`task.md` 记录授权、标准、路径、分支、基线、阶段、轮次和恢复入口；主控写任务定义及角色输入。每份 input/output 标明轮次和所处理的实现版本。
- 主控检查 develop、现有认领和任务材料，确认没有重复领取；从 develop 已提交版本创建或复用独立任务 worktree，只在原目录登记或更新认领。恢复或返工沿用原分支与 worktree。开发和验收命令明确指向该 worktree。
- 主控以不继承完整对话的独立上下文派发开发与验收；业务要求、决策和证据通过上述文件传递，工具指令只传路径和生命周期信号。角色按任务范围读取所需材料，不读取对方通信目录。
- 开发只在任务 worktree 实施，只读已批准材料和自己的通信目录，只写自己的 output、任务实现及所属文档。验收独立固定本轮实现，只写自己的 output；可运行检查并产生临时结果，不修改实现或标准。
- 机械且步骤明确的任务优先给可用的低成本模型；复杂判断按任务难度选择模型。

**边界说明：**上述角色职责、目录和派发分工是 skill 明文；将“材料文件承载业务沟通、工具调用只承载路径和生命周期信号”概括为工具与业务通信的分工，是对该明文的归纳。skill 没有要求在这里补充特定工具、命令、模型名称或额外审批步骤。

## H. 计划确认、实际交付确认与集成

- 只有计划确认，没有用户对当前实际交付的确认：独立验收通过后，在任务分支本地提交已验收实现及报告，保留 worktree；任务分支状态记为“已完成，待人工确认”，develop 路线图仍为“进行中”并保留认领。不推送、不合入；等待用户决定。
- 用户明确确认当前实际交付并要求集成：主控才在一次集成提交中合入 develop，标记主线任务“已完成”，移除已结束认领，并验证受影响范围。默认不推送。完成集成后等待用户决定下一项，不自动开始下一任务。

依据：计划确认不等于集成许可；只有用户确认实际交付后才按 skill 所述集成。不能把“待人工确认”写成 develop 完成状态。

## I. 文档冲突或必要功能项未执行

- 功能和代码通过，但 README 与真实行为相反：文档检查未通过，整轮不能判通过。按本任务改动及受影响入口检查并修正文档，再重新完成必要验收。
- 必要功能项没有执行：不能判通过。skill 明确规定功能验证、代码审查或文档检查任一必要项未执行，都不能判通过。

依据：验收依次检查功能标准、代码差异和文档，且任一必要项未执行不能通过。两种场景当前都不能声称验收通过。
