# 单任务持续开发与验收

在当前会话内把一个任务推进到独立验收，并交付可审阅结果。复用会话、子 agent 和 worktree；不新增后台服务、定时自动化或跨任务队列。结束后等待用户决定下一项。

## 启动与认领

遇到适合多轮开发和独立验收的任务时，向用户提议本流程；用户明确要求使用时不再询问是否启用。开始前确认范围、方案和功能验收标准。用户已确认的内容不重复询问；其余未授权的标准不能自行设定、降低或替换。

检查 develop、现有认领和任务材料，确认任务未被重复领取。主控从 develop 的已提交版本创建或复用独立任务 worktree；恢复或返工时沿用原任务分支和 worktree。开发与验收命令始终明确指向该 worktree。只在原目录登记或更新认领。

在任务 worktree 建立以下材料，并由主控维护任务定义及角色输入：

```text
docs/ai/<任务名>/
├── task.md                 # 主控：授权、标准、路径、分支、基线、阶段、轮次和恢复入口
├── developer/
│   ├── input.md            # 主控写；开发读
│   └── output.md           # 开发写；主控读
└── verifier/
    ├── input.md            # 主控写；验收读
    └── output.md           # 验收写；主控读
```

每次 input 和 output 标明轮次与被处理的实现版本。主控冻结验收版本并记录可核对的代码状态（提交号及工作区变更/文件内容摘要）；主控读取本轮验收报告，确认轮次和版本匹配后才采用结论。过期报告或工具通知中的“通过”文字不构成本轮验收。

## 分工与证据

- 主控使用不继承其完整对话的独立上下文派发开发和验收。业务要求、决策和证据经上述文件转交；工具指令只传路径和生命周期信号。角色按任务范围读取实现、需求和必要证据，不读取对方通信目录。这是上下文与职责隔离，不代表操作系统权限隔离。
- 开发只在任务 worktree 实施；只读已批准材料和自己的通信目录，只写自己的 output、任务实现及其所属文档。
- 验收独立固定本轮实现。验收期间暂停开发；验收只写自己的 output，可运行检查并产生临时结果，但不修改实现或标准。验收完成前不恢复开发。验收之后任何实现变化都必须重新验收。
- 机械、步骤明确的任务优先分配给可用的低成本模型；需要复杂判断时按任务难度选择模型。
- 正式证据放在所属模块、应用或数据集；逐轮执行记录留在 `docs/ai/`。明确区分已检查、仅确认启动和未执行。模拟场景必须标为模拟，不能替代真实功能验收。

## 判断与验收

从用户的使用目的和错误代价判断方案。必要时用实际案例核对人工判断与指标排序；若指标不能代表用户价值，说明案例和建议并请用户确认，不自行改变标准。

验收依次检查功能标准、代码差异和文档。三项分别给结论；功能验证、代码审查或文档检查任一必要项未执行，都不能判通过。关键验证由验收方独立重跑；耗时实验检查完整证据，有疑点时重跑。文档只检查本任务改动及受影响入口，按 AGENTS.md 的准确、易读、简洁要求判断。

一轮包含一次开发交付及其对应的独立验收。以目标改善、检查通过、阻塞解除或推动后续的新证据判断进展；重复检查或改写说法不算进展。相邻两轮无提升时主控调整思路；连续三轮无实质进展时停止子 agent 和本任务相关运行，保存材料并等待用户。权限、数据、环境或标准决策缺失时，停止依赖该条件的步骤并请用户决定。

用户明确恢复后，复用原材料、认领、分支和 worktree；保留历史轮次与证据，新的连续停滞计数从 0 开始。

## 交付和状态

独立验收通过后，在任务分支本地提交已验收实现及报告，保留 worktree，不推送、不合入。仅此工作流的任务分支状态记为“已完成，待人工确认”；develop 路线图保持“进行中”并保留认领。用户要求修改时在原分支返工并复验。用户确认实际交付后，主控才在一次集成提交中合入 develop、标记主线任务“已完成”、移除结束的认领并验证受影响范围。不得在 develop 写入“已完成，待人工确认”；默认不推送。方案确认不等于集成许可。之后等待用户决定下一项。
