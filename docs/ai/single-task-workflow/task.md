## 已确认范围和方案

1. 创建仓库 skill `run-task-workflow`，复用当前会话、子 agent 与 worktree，无后台服务、自定义执行器或自动跨任务。
2. 主控识别适用任务，启用前先询问；已有明确授权不重复询问。启动时必须与用户明确范围、方案和功能验收标准，除非明确授权不得自定、降低或替换标准。未确认时不派发开发。
3. 主控从使用目的和错误代价审视方案与指标。剪掉有效回合一秒和落地后多留一秒的代价不同，应发现指标失真，提出有案例依据的指标并请用户确认。本 P0 不修改算法或自行设数值指标。
4. 主控、开发、独立验收三角色。机械任务优先成本较低的可用模型；复杂判断按能力选择。
5. 开发在独立任务 worktree；启动后于其 `docs/ai/<任务名>/` 创建本目录结构。只读已批准的任务材料与自己的通信目录，按范围阅读代码、需求及必要证据。
6. 子 agent 不继承主控完整对话，不直接通信、不自行读取对方通信报告。业务内容通过文档，主控唯一中转；工具只传路径和生命周期指令。此为上下文/职责隔离，不虚构操作系统文件权限隔离。
7. 主控写 task.md、两个 input.md；开发只写自己的 output.md 和任务实现/文档；验收只写自己的 output.md，可运行检查产生缓存/临时结果，不修改实现或标准。
8. 验收三个独立步骤：功能验收、代码审查、文档验收。独立重跑关键验证；耗时大实验核对完整证据，有疑点重跑。必要项未执行不能记通过。
9. 文档按 AGENTS 的准确、易读、简洁核验，仅本次改动及受影响文档，不扩成全仓清理。正式证据归所属模块/应用，执行流水归 docs/ai，不进人类文档站。
10. 一轮=一次开发尝试及对应独立验收。有进展以确认目标的改善、检查通过、阻塞解除或推动后续的新证据为准，不以改说法/重复检查计进展。
11. 相邻两轮无提升时主控排查并调整思路；连续三轮无实质进展停止子 agent/本任务相关运行，保存材料并等待人工。必要权限/数据/环境或范围/标准决策缺失及时询问。
12. 恢复复用原认领、分支、worktree 和记录；明确恢复后重新开始连续停滞计数。当前任务结束不自动领取下一项。
13. 验收期间暂停开发，固定本轮检查版本，最终提交对应已验收实现；后续实现变化须复验。
14. 验收通过在任务分支本地提交并保留 worktree，状态“已完成，待人工确认”，不推送、不合入。develop 仍“进行中”并保留认领。
15. 人工要求修改则原分支返工复验。人工对实际交付明确确认后，主控更新 roadmap 并一次集成到 develop：主线任务由“进行中”到“已完成”，不提交“待人工确认”中间状态；移除已结束认领并验证受影响范围。默认不推送，既有修改不夹带/覆盖。计划确认不是合入许可。
16. 改动限 skill、AGENTS 的简短入口/第一性原则及状态规则、roadmap 中 P0 范围/协作约定和本任务记录。保留其他任务、优先级、Windows/性能负责人和斜体标记；不改变产品接口。

## 本 P0 已获确认的验收标准

- skill 格式正确，能被自动发现，但执行前有明确启用/标准确认关口。
- 在隔离临时仓库实际演练成功和返工路径：真实开发、文档通信、独立功能检查、代码审查、文档检查、本地提交，最终等待人工。
- 未确认启用或功能标准时不开发；功能或文档失败不通过；两轮无提升调整、三轮停滞停等；指标失真主动提出问题但不擅改口径；人工要求修改/中断恢复使用原目录和分支；人工确认前不合入不推送；确认后状态同步合入；原目录已有修改和其他任务保持完整。
- 控制分支可以用明确标注的模拟场景演练，模拟不能充当真实功能验收；记录实际执行与未执行。
- 执行既有 skill quick_validate、git diff --check 和文档构建；本任务不改产品，产品测试不要求。
- 对当前交付给出独立验收结论。任何未覆盖必要项目都不能宣布通过。
